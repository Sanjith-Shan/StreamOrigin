# Bug log

Every bug found while building StreamOrigin, with the tool or check that found it. Newest last.

| # | Date | Component | Symptom | Found by | Cause | Fix |
|---|---|---|---|---|---|---|
| 1 | 2026-09-27 | packager, edge-sim | Every packager PUT failed with HTTP 501 while `curl` to the same URL got 201 | Packager's first-error line, then `lsof -iTCP:8080` | An unrelated local Python server held IPv4 `*:8080`; the JDK client resolved `localhost` to 127.0.0.1 and reached it, while curl reached the Java server on IPv6 | All StreamOrigin ports moved to the 27xxx block |
| 2 | 2026-09-27 | edge-sim | M1 play-through lost exactly one segment (k=44) on all 30 cache-renditions, with 718 bare `IOException`s | Fleet's `missing_segments` report plus the printed cause chain: `RejectedExecutionException` | The fleet shut down its virtual-thread executor to wait for in-flight fetches, but the `HttpClient` ran on that same executor, so every request still open for the last segment was rejected | `HttpClient` gets its own executor that is never shut down (same fix applied to the packager) |
| 3 | 2026-09-27 | edge-server admission | Under a 100-cache storm with no DVR traffic at all, 257 live-edge requests got 503, and publish-to-first-byte p99 jumped to 5 s (the shed caches waited out `max-age=5`) | exp1 calibration run: fleet `live.status.503` counter | Both classes shared one adaptive limit. Serving 300 MB in one burst inflated service time, the gradient limit shrank to its floor, and live requests were shed along with DVR | Live-edge admission is now capped at max(adaptive limit, a fixed live floor of 512); only DVR follows the adaptive limit |
| 4 | 2026-09-27 | environment (Docker Desktop) | During a DVR capacity sweep at 1,200 requests/s with priority off, the edge lost its Redis connection (2,593 `Connection closed`), live caches missed 1,500 deliveries, and then `docker ps` itself returned HTTP 500 until Docker Desktop was restarted | exp5 calibration: edge log, then `docker info` | Roughly 800 MB/s of Redis reads through Docker Desktop's userspace network stack on macOS took the Docker VM's networking down | Not a StreamOrigin bug. The overload experiment now runs on the embedded RocksDB store in one process, so its load never crosses the Docker network; experiments that need Redis stay below that bandwidth |
| 5 | 2026-09-27 | edge-server cache | DVR capacity sweep showed a DVR p50 of 0 ms at 800 requests/s: the "store" was never being read | exp5 calibration: `dvr.request_us` p50 plus the edge's `store.data_reads` counter | Every store read was written into the live-edge cache, so the whole 40-segment DVR window became cache-resident. It hid the store's real cost and, at a longer window, would evict the live edge | Store reads fill the cache only for `LIVE_EDGE` requests; DVR reads always go to the read store (still coalesced) |
| 6 | 2026-09-27 | edge-sim (open) | exp1 `designed-shared` at 100 caches reported 4 and then 34 "corrupt delivered" segments in two of three repeats, with both pipelines healthy and nothing injected | Fleet `live.delivered_corrupt` counter; the other 80 exp1 to exp3 runs of the designed origin showed 0 | Not confirmed. The fleet counted any exception while streaming a body as a zero-length, hence corrupt, delivery, so a transfer cut short under the heaviest single-process load would look like corruption. All of those responses came from held requests answered with write-through bytes, and the origin logged no errors | The fleet now checks the body length against `Content-Length`, counts a short or failed read as `live.truncated`, retries it as a cache would, and prints the first bytes of anything it still calls corrupt. Three re-runs of the same configuration (`results/exp1_diag.jsonl`) showed 0 truncated and 0 corrupt. The original rows stay in `results/exp1.jsonl` |
| 7 | 2026-09-27 | edge-sim junk generator | In exp4's first run the designed origin rejected only 75% of junk requests at the control plane; 11,069 still reached the store | exp4 run 0: edge `cp.reject` against fleet `junk.requests` | The "older than the DVR window" category computed `edge - window - 50`, clamped at 0. In a one-minute-old event with a 150-segment window that is segment 0, which is inside the window and legitimately looked up | exp4 runs with a 10-segment DVR window so stale requests are really stale; the three rows already recorded were discarded and exp4 re-run |
| 8 | 2026-09-27 | harness | After the first exp5 run (priority off at 1.5x capacity collapsed the origin), Docker Desktop hung again, and the next run's `docker compose exec redis-cli FLUSHALL` blocked the suite indefinitely. A clean restart then failed behind a "running processes prevent startup" dialog until every Docker process was force-killed | Suite stalled; `docker ps` did not return; Docker backend log | Same host starvation as bug 4, now from a collapsed origin plus a 2,400 req/s fleet on one laptop. The harness assumed Docker was always there | exp5 runs no longer touch Docker (embedded RocksDB, no flush). The harness waits for `docker info` before any run that needs Redis and prints `DOCKER UNHEALTHY` instead of hanging. Priority off runs only at 1.5x; 2x runs only with priority on, since 1.5x already collapses the origin without it |
| 9 | 2026-09-27 | edge-server admission and process layout | exp5 with priority on at 1.5x capacity collapsed as badly as with it off: 150 of 2,250 live deliveries, write p99 5.6 s, and only 3,452 of 72,000 DVR requests refused | exp5 run: origin counters `store.writes` = 28 for the whole run, `shed.dvr.limit` = 3,452, final `admission.limit` = 19 | Two things. The publish PUTs shared Netty's event loops with the DVR flood, so segments stopped landing and every held live request timed out; no serve-side priority can fix a starved write path. And the adaptive limit only sees time spent inside the handler, while the queue built up before it (socket reads and the event loop), so the limit barely engaged | In one process the publish path now runs on its own port and event loops (`origin.publish-port`), the in-process version of separate stacks. With priority on, the DVR token bucket is set to the measured capacity, so excess replay requests get a cheap 503 before any work is done. exp5 was re-run from scratch; the earlier rows are kept in `results/exp5_v1.jsonl` and `results/exp5_capacity_v1.jsonl` |
| 10 | 2026-09-27 | scripts/demo.sh | After restarting the demo, a fleet against it reported publish-to-first-byte at the 120 s histogram ceiling for almost every segment | Fleet `live.publish_to_first_byte_us` during the Grafana capture run | The demo reused event id `demo` with a new epoch but did not clear Redis, so segment numbers from the previous run were still in the store (10-minute TTL) and first-valid selection served the old copies. The experiment harness always flushed, so no ledger row was affected | `demo.sh` flushes both stores before starting. A production origin would key segments by an event run id as well as the event id |
